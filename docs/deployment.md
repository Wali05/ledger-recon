# Run and deploy

## Recommended public demo: Vercel

The frontend is a static Vite application. A production build with no API URL defaults to the demo. It includes fictional sample results generated by the real Python matcher, CSV export, filtering, sorting, evidence review and browser-local resolutions. No database, queue, provider key or backend is needed.

In Vercel, import the GitHub repository and use:

| Setting | Value |
| --- | --- |
| Root Directory | `frontend` |
| Framework | Vite |
| Node.js | 24.x |
| Install command | `npm ci` |
| Build command | `npm run build` |
| Output directory | `dist` |
| Environment variables | None for the default demo |

`frontend/vercel.json` records the framework/build settings and basic response headers. Keep repository files outside `frontend` out of the build root. When connecting an existing Vercel project, remove a stale `VITE_API_BASE_URL` or explicitly set `VITE_DEMO_MODE=true` for the public demo.

The UI labels this as an interactive demo. **Replay** reloads precomputed results; it does not execute Python. **Resolve** affects this browser only; **Reset demo** restores the sample. File uploads are unavailable in this mode.

For a local production preview:

```sh
cd frontend
npm ci
npm run build:demo
npm run preview
```

Open the URL printed by Vite. Its preview server is for local verification. Follow the [Vite deployment guide](https://vite.dev/guide/static-deploy.html#vercel) and [Vercel Vite documentation](https://vercel.com/docs/frameworks/frontend/vite) for hosting settings. A local build passing does not confirm a deployed URL; this repository does not contain an automated deployment workflow.

## Full workflow on your computer

Use Python 3.12 and Node.js 24. From the repository root:

```sh
python -m venv .venv
```

Activate with `.venv\Scripts\Activate.ps1` in PowerShell, or `source .venv/bin/activate` on Linux/macOS. Then:

```sh
python -m pip install -r backend/requirements.txt
python -m uvicorn app.main:app --app-dir backend --reload
```

In another terminal:

```sh
cd frontend
npm ci
npm run dev
```

Open `http://localhost:5173` and select **Run reconciliation**. The development frontend proxies API requests to `http://localhost:8000`. Interactive API documentation is at `http://localhost:8000/docs`.

By default, the API creates `backend/ledger_recon.db`, independent of the terminal's working directory. No environment file is required. To load overrides from a copied root `.env.example`, add `--env-file .env` to the API command. The example contains comments; uncomment only the settings you need.

To try uploads, select **Your CSV files**, choose `samples/ledger.csv` and `samples/statement.csv`, upload both, then run reconciliation. Replacing a changed pair removes the previous uploaded results and run history; unchanged bytes preserve them.

## PostgreSQL and a separate worker

With Docker Desktop/Engine running:

```sh
docker compose up --build --wait
```

This starts PostgreSQL 16, Redis 7, the API, a Celery worker and the development dashboard. Open `http://localhost:5173`. The API is on port 8000; database and Redis ports are not published. Web ports bind to loopback. Named volumes retain local database and broker state after `docker compose down`.

Optional root environment settings include `API_PORT`, `UI_PORT` and `POSTGRES_PASSWORD`. The supplied password is a local development default. The frontend container runs Vite's development server; Compose is a reproducible local stack, not a public hosting blueprint.

```sh
docker compose logs --tail 100 backend worker
docker compose down
```

## Connect the dashboard to a hosted API

A free, working setup: PostgreSQL on [Neon](https://neon.tech), the API on [Render](https://render.com) and the dashboard on Vercel. Jobs run inside the API process, so no Redis or worker is needed. Free hosts sleep when idle; the first request after a pause can take about a minute.

1. **Database.** Create a Neon project and copy its connection string (`postgresql://…?sslmode=require`). The SSL options are translated for both database drivers.
2. **API.** In Render, create a **Web Service** from this repository with **Root Directory** `backend` and runtime **Docker**. Set the health check path to `/health` and add these environment variables:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | Neon connection string |
   | `API_KEYS` | `yourname:<32+ random characters>` (add more `name:key` pairs separated by commas) |
   | `ALLOWED_ORIGINS` | Your Vercel URL, e.g. `https://ledger-recon.vercel.app` (no trailing slash) |

   Migrations run on startup. Open `https://YOUR-API.onrender.com/health` and expect `"status":"ok"`.
3. **Dashboard.** Create a second Vercel project from the same repository (Root Directory `frontend`) with these build-time variables, then deploy:

   ```dotenv
   VITE_API_BASE_URL=https://YOUR-API.onrender.com
   VITE_DEMO_MODE=false
   ```

   Sign in with one of your keys, run the sample dataset and upload the sample CSVs.

Keep the first Vercel project as the public demo link. The connected one needs a key, so share keys only with people you want to review data.

**Separate worker (optional).** To use the queued mode, add Redis (for example Upstash or Render Key Value) and set `CELERY_BROKER_URL` and `REDIS_URL` on the API. Then run a second service from the same image with the command `celery -A app.celery_app worker --loglevel=info --concurrency=2` and the same variables plus `AUTO_MIGRATE=false`. Without `CELERY_BROKER_URL`, run exactly one API instance.

Every `VITE_` variable is public browser code. Never put an API key, Gemini key, broker URL or database password there. Health confirms database access, not worker availability.

## Optional AI explanations

AI is disabled by default. On the API server, install `backend/requirements-ai.txt` and set `GEMINI_API_KEY`; `GEMINI_MODEL` can override the configured model. For Compose, set `INSTALL_AI=true` and the server key, then rebuild. Provider availability and cost are outside the demo. Generated text is a hypothesis and may be incorrect. Provider failures are reported without hiding the rule evidence or changing resolution state.
